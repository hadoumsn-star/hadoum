## 2. Prisma migration strategy (PR 1 — additive only)

### `ContactCategory`

```
model ContactCategory {
  id        String   @id @default(uuid())
  key       String   @unique
  label     String
  color     String?
  sortOrder Int      @default(0)
  active    Boolean  @default(true)

  contacts  Contact[]

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}
```

### `Contact`

```
model Contact {
  id             String   @id @default(uuid())

  fullName       String
  organization   String?
  functionTitle  String?

  categoryId     String
  category       ContactCategory @relation(fields: [categoryId], references: [id], onDelete: Restrict)

  phone          String?
  whatsappEnabled Boolean @default(false)
  email          String?
  address        String?
  city           String?
  notes          String?

  photoKey       String?
  photoMime      String?

  active         Boolean  @default(true)

  createdAt      DateTime @default(now())
  updatedAt      DateTime @updatedAt

  supplierContracts        SupplierContract[]
  administrativeProcedures AdministrativeProcedure[]
  maintenanceTickets       MaintenanceTicket[]
  transactions             Transaction[]

  @@index([categoryId])
  @@index([active])
  @@index([fullName])
}
```

`onDelete: Restrict` on `Contact → ContactCategory`: a category cannot be deleted (only deactivated) while any contact still references it — matches how `MaintenanceTicket → Space` already uses `onDelete: Restrict` for the same "don't orphan business data" reason.

### Relation fields on the four consuming models

| Model | New Prisma field | New FK column | Relation name | Nullability | `onDelete` |
|---|---|---|---|---|---|
| `SupplierContract` | `supplierContact` | `supplierContactId` | `SupplierContractContact` (explicit name needed — see below) | `String?` (nullable) | `SetNull` |
| `AdministrativeProcedure` | `contact` | `contactId` | default (single relation to Contact from this model) | `String?` (nullable) | `SetNull` |
| `MaintenanceTicket` | `assigneeContact` | `assigneeContactId` | default | `String?` (nullable) | `SetNull` |
| `Transaction` | `supplierContact` | `supplierContactId` | `TransactionSupplierContact` (explicit name needed — see below) | `String?` (nullable) | `SetNull` |

**Why `onDelete: SetNull` here, not `Restrict`:** these four relations point *from* business records *to* a Contact — the opposite direction of the category relation above. If a contact is later hard-removed (not expected in normal operation, since §3 exposes no hard-delete endpoint, but a DBA/support action could still do it directly), the business record itself (the contract, the ticket, the expense) must **not** be blocked from existing or be deleted as a side effect — it should simply lose the link and keep functioning with its legacy free-text field, which is still present and populated throughout this entire plan. `SetNull` is the only behavior consistent with "never lose or block a business record because of something that happened to a contact."

**Why two relation names need to be explicit:** Prisma requires a named relation whenever a model has more than one relation to the same target type. Because both `Contact` and (later, if ever) another model could each define a relation into the same target, and because `Contact`'s reverse-relation list already names four back-references from four different models, most of these are unambiguous by model pair alone — **except** if `SupplierContract` or `Transaction` ever need a second, distinct Contact relation later (e.g., `Transaction` gaining both a `supplierContact` and a separate `approvedByContact` down the line). To avoid a breaking rename later, this plan assigns explicit relation names to `SupplierContract.supplierContact` and `Transaction.supplierContact` now, since "supplier" is a role-specific relation (not just "the" contact for that record) — `AdministrativeProcedure.contact` and `MaintenanceTicket.assigneeContact` can stay on Prisma's default relation naming since each currently has only one Contact relation and no foreseeable second one in this plan.

**Corresponding reverse fields on `Contact`** (already shown above): `supplierContracts SupplierContract[]`, `administrativeProcedures AdministrativeProcedure[]`, `maintenanceTickets MaintenanceTicket[]`, `transactions Transaction[]`.

**What this migration does NOT do**, matching the brief exactly: it does not remove `SupplierContract.supplierName`/`.contactPerson`/`.phone`/`.email`/`.address`, `AdministrativeProcedure.authority`/`.assignedTo`, or `MaintenanceTicket.assignedTo`. It does not add any `NOT NULL` constraint to a new relation. It does not touch `Transaction` beyond adding the one new nullable column (there is nothing to preserve there — confirmed no existing supplier-shaped field exists on `Transaction` today).

### Photo: reuse the existing S3 convention, direct fields — not a separate document table

**Decision: `photoKey`/`photoMime` as direct columns on `Contact`, using the existing generic `UploadService`, exactly as specified in the brief. Not a separate document table.**

This codebase already has both patterns and the choice between them is not ambiguous once the actual precedent is checked:
- **Direct key/mime-ish field(s) on the owning model** — used by `StaffMember.cvKey`/`.scheduleKey` for "this entity has exactly one of this kind of file."
- **A separate `*Document` table** (`ContractDocument`, `ProcedureDocument`, `TicketAttachment`, `SpaceDocument`, `StockItemDocument`, `InventoryAssetDocument`, `EntryLogDocument`) — used everywhere an entity can have **multiple, independently-labelled** attachments.

A contact photo is a single, singular avatar-like file per contact — the same shape as `StaffMember.cvKey`, not the shape `ContractDocument` exists for. `Contact.photoMime` (which `StaffMember.cvKey` notably lacks — `StaffMember` has no `cvMime`) is a deliberate small improvement over that precedent, since a photo specifically needs its MIME type to render an `<img>` correctly or validate it's actually an image at upload time — this is additive precision, not a deviation from the established pattern.

Backend usage: `POST /contacts/:id/photo` (multipart) calls the existing `uploadService.upload(file, 'contacts')` — same call shape every other module already uses (e.g. `uploadService.upload(file, 'contracts')` in `supplier-contracts.service.ts`) — storing the returned key in `Contact.photoKey` and `file.mimetype` in `Contact.photoMime`. Retrieval goes through the same existing `uploadService.getPresignedUrl(key)` pattern every other module's `GET .../url` endpoint already uses. **No change to `upload.service.ts` or `upload.module.ts` is needed** — its API is already generic enough.

## 3. Incremental implementation order

### PR 1 — Database foundation and backend Contact CRUD

- **Goal:** stand up `Contact`/`ContactCategory` end-to-end on the backend, fully isolated, with no consuming module touched.
- **Files affected:** all "Create" rows under Prisma and NestJS backend in §1, plus `app.module.ts` registration. No frontend files.
- **Database impact:** additive migration only (two new tables, four new nullable columns on unrelated-so-far-because-unused fields — actually, to keep PR 1 *strictly* about Contact/ContactCategory, the four consuming-model FK columns can be deferred to each integration PR instead of all added upfront. **Recommendation: add all four nullable FK columns in PR 1's migration anyway**, even though they're unused until PR 3-6, because (a) it's one additive migration instead of five smaller ones touching the same models repeatedly, and (b) an unused nullable column carries zero behavioral risk. This is the one deliberate deviation from "one PR = one migration" in this plan, justified by migration-count hygiene outweighing the near-zero risk of an inert column.
- **API impact:** new, previously-nonexistent endpoints only (§4). Nothing existing changes shape.
- **UI impact:** none.
- **Tests to add:** `contacts.service.spec.ts` (unit, mocked Prisma per the existing `Test.createTestingModule` convention used by the other nine `*.service.spec.ts` files), `test/contacts.e2e-spec.ts` (real Postgres, real HTTP, following `documents.e2e-spec.ts`'s shape as the closest analog since it's also upload-plus-CRUD).
- **Manual verification steps:** `POST /contacts` with a minimal payload succeeds and returns the created row; `GET /contacts/search?q=...` returns matches; creating a second contact with the same phone number returns the duplicate-warning shape (§4) rather than a hard error; `PATCH /contacts/:id/deactivate` as SUPERVISOR is rejected with 403; the same as DIRECTOR succeeds and the contact drops out of default `GET /contacts` results; `POST /contacts/:id/photo` with a small JPEG succeeds and `GET /contacts/:id/photo-url` returns a working presigned URL.
- **Rollback strategy:** revert the PR's commit(s); the migration is purely additive (new tables, nullable columns with no data written to them by anything else yet), so `prisma migrate resolve --rolled-back` / a down-migration dropping the two new tables and four new columns is safe with zero data loss, since nothing outside this PR reads or writes them.
- **Dependencies on previous PRs:** none — this is the foundation.

### PR 2 — Shared frontend `ContactAutocomplete` and inline creation

- **Goal:** build the reusable selector and creation flow against the real API from PR 1, proven in isolation (e.g., a throwaway/demo usage, or directly wired into the first real integration if PR 3 is bundled — see note below) before any production form depends on it.
- **Files affected:** all "Create" rows under "Frontend services and types" and "Reusable frontend components" in §1.
- **Database impact:** none.
- **API impact:** none (consumes PR 1's endpoints only).
- **UI impact:** none yet visible to end users unless bundled with PR 3.
- **Tests to add:** `hadoum_frontend/e2e/contacts.spec.ts` covering the autocomplete's search/keyboard/category-filter/inline-creation behavior — this requires *some* real page to mount the component on to be testable end-to-end; **recommendation: merge PR 2 and PR 3 into a single PR in practice**, since a component with no consumer is untestable through the UI and this plan's own §9 requires Playwright coverage of the integrated behavior, not the component in a vacuum. Kept as two conceptual steps here (component design vs. first integration) because the brief asks for that separation, but sequencing them as one reviewable change is the safer real-world choice.
- **Manual verification steps:** typing in the autocomplete returns filtered results within the debounce window; arrow keys move the highlighted option and wrap correctly at the ends; Enter selects; Escape closes without changing the bound value; selecting "+ Créer un nouveau contact" opens the modal without losing the parent form's other field values; submitting the inline-create modal auto-selects the new contact and closes the modal.
- **Rollback strategy:** revert the commit(s); no schema or data involved.
- **Dependencies:** PR 1 (needs real endpoints to call).

### PR 5 — Supplier Contract integration

- **Goal:** the highest-value, highest-complexity integration — collapses five free-text fields (`supplierName`, `contactPerson`, `phone`, `email`, `address`) into one relation.
- **Files affected:** `supplier-contracts.service.ts`, `.controller.ts`, `dto/create-supplier-contract.dto.ts`, `dto/update-supplier-contract.dto.ts`, `SupplierContractsPage.tsx`, and — **specifically** — the `SUPPLIER_CONTRACT` case in `validations.service.ts`'s `findPending()` `select` block (currently selects `supplierName`; needs `supplierContact: { select: { fullName: true, organization: true } }` added alongside it, not instead of it, during the transition).
- **Database impact:** none new (nullable `supplierContactId` already exists from PR 1).
- **API impact:** `POST`/`PATCH /supplier-contracts` gain optional `supplierContactId`. All 7 notification-message call sites identified in §7/§10 need their string interpolation updated to prefer the linked contact's name when present, falling back to the legacy `supplierName` field when not (dual-read, not a breaking change).
- **UI impact:** the supplier-name/contact-person/phone/email/address block in `SupplierContractsPage.tsx`'s create/edit modal collapses to one `ContactAutocomplete`, category-filtered toward `FOURNISSEUR`.
- **Tests to add:** update `supplier-contracts.service.spec.ts` (existing assertions constructing a contract via raw `supplierName` need a decision — see §10 — either keep working via the legacy field, or add new cases for the `supplierContactId` path); update `test/lifecycle-scenarios.e2e-spec.ts` similarly.
- **Manual verification steps:** create a contract via the autocomplete; confirm the notification text generated on submit-for-validation shows the contact's name correctly; confirm a contract created before this PR (legacy `supplierName` only, no relation) still displays and generates correctly-worded notifications from its legacy field; confirm the existing two-actor validation flow (DIRECTOR submits, SUPERVISOR approves/rejects) still works unchanged.
- **Rollback strategy:** revert; legacy fields were never removed, so a full rollback loses nothing.
- **Dependencies:** PR 1, PR 2. (Not dependent on PR 3/4 — order among PR 3/4/5/6 is otherwise flexible; sequenced this way per the brief's own suggested order and because it's the most complex, benefiting from the pattern being proven twice already on simpler modules first.)

### PR 6 — Administrative Procedure integration

- **Goal:** integrate the external-authority/responsible-person concept.
- **Files affected:** `administrative-procedures.service.ts`, `.controller.ts`, `dto/create-administrative-procedure.dto.ts`, `dto/update-administrative-procedure.dto.ts`, `DemarchesAdministrativesPage.tsx`, the `ADMINISTRATIVE_PROCEDURE` case in `validations.service.ts`'s `findPending()`.
- **Database impact:** none new (nullable `contactId` already exists from PR 1).
- **UI decision resolved by inspection** (the brief's open question): `authority` (label **"Autorité \*"**, required, placeholder "Ex : DGPJS") and `assignedTo` (label **"Responsable"**, optional, placeholder "Personne en charge du dossier") are two **distinct, already-separate** fields in the current form — not one field with an ambiguous label as the earlier design doc speculated. Recommendation: **keep both labels exactly as they are**, and let `AdministrativeProcedure.contact` back the "Responsable" field specifically (a named person), while `authority` remains free text for now (the organization name) rather than forcing both into one relation. This is more conservative than collapsing them, avoids guessing which of "the org" or "the person" a single Contact selection is supposed to represent, and matches the fact that a Contact can itself hold both `fullName` (person) and `organization` (org) — so a future follow-up (**out of scope for this PR**) could let selecting a "Responsable" contact auto-suggest `authority` from that contact's `organization` field, without this PR needing to decide that now.
- **API impact:** `POST`/`PATCH /administrative-procedures` gain optional `contactId` (backing "Responsable"). `authority` is untouched. All notification-message call sites using `procedure.authority` are **not** changed by this PR (since `authority` itself isn't becoming a relation here) — only worth revisiting if a future PR migrates `authority` too.
- **UI impact:** the "Responsable" free-text input becomes `ContactAutocomplete`, category-filtered toward `ADMINISTRATION`. "Autorité" stays a plain text input, unchanged.
- **Tests to add:** update `administrative-procedures.service.spec.ts` and `test/lifecycle-scenarios.e2e-spec.ts` for the new optional `contactId` field on "Responsable" only.
- **Manual verification steps:** create/edit a procedure, assign a "Responsable" contact via the autocomplete, confirm it persists and displays; confirm "Autorité" continues to work exactly as before (no regression, since it isn't touched); confirm the reject-without-comment-blocked and archive-confirmation behaviors (verified working in the earlier QA campaign) are unaffected.
- **Rollback strategy:** revert; `authority` was never touched, `contactId` stays nullable/unused.
- **Dependencies:** PR 1, PR 2.

## 4. Backend API contract

**Decision on the "two search implementations" question: one endpoint, one implementation, two response shapes via a query flag.** `GET /contacts` serves both the directory page and the autocomplete through a `?compact=true` option (or equivalently, `?fields=compact`) — not two separate endpoints or two separate service methods. The underlying Prisma query (search/filter/pagination logic) is identical either way; only the `select` clause differs (compact: `id`, `fullName`, `organization`, `category.label`, `active`; full: every field). A second endpoint (`GET /contacts/search`) was proposed in the earlier architecture doc as a "lightweight, fast" path, but there is no actual performance justification for that split at this data scale (a contact directory numbering in the dozens-to-low-hundreds, per the earlier audit's reasoning) — the brief's own instruction to avoid two search implementations "unless there is a clear performance need" is correctly answered here: there isn't one.

| Method | Route | Request | Response | Roles | Notes |
|---|---|---|---|---|---|
| `GET` | `/contacts` | Query: `search?`, `categoryId?`, `active?` (default `true`), `compact?` (default `false`), `page?`, `pageSize?` | `{ data: Contact[] \| CompactContact[], total: number }` | DIRECTOR, SUPERVISOR | `search` matches `fullName`, `organization`, `functionTitle`, `phone`, `notes` (category is matched via `categoryId`, not the text search — see rationale below) |
| `GET` | `/contacts/:id` | — | `Contact` (full shape) | DIRECTOR, SUPERVISOR | 404 if not found; **inactive contacts are still returned** (not filtered) — needed so a form referencing a now-inactive contact can still render it, per the brief's inactive-display requirement |
| `POST` | `/contacts` | `CreateContactDto` | `Contact`, or `{ possibleDuplicate: CompactContact, message: string }` with `409` | DIRECTOR, SUPERVISOR | see duplicate-warning behavior below |
| `POST` | `/contacts?force=true` | same | `Contact` | DIRECTOR, SUPERVISOR | bypasses the duplicate warning after the user confirms they want to create anyway |
| `PATCH` | `/contacts/:id` | `UpdateContactDto` (all fields optional; `active` excluded — see below) | `Contact` | DIRECTOR, SUPERVISOR | |
| `PATCH` | `/contacts/:id/deactivate` | — | `Contact` (with `active: false`) | **DIRECTOR only** | |
| `PATCH` | `/contacts/:id/reactivate` | — | `Contact` (with `active: true`) | **DIRECTOR only** | |
| `POST` | `/contacts/:id/photo` | multipart `file` | `Contact` (with `photoKey`/`photoMime` set) | DIRECTOR, SUPERVISOR | mirrors every other module's upload-then-return-updated-entity convention |
| `GET` | `/contacts/:id/photo-url` | — | `{ url: string; expiresIn: number }` | DIRECTOR, SUPERVISOR | mirrors `GET .../documents/:id/url` conventions used elsewhere |
| `DELETE` | `/contacts/:id/photo` | — | `Contact` (with `photoKey`/`photoMime` cleared) | DIRECTOR, SUPERVISOR | |
| `GET` | `/contacts/categories` | Query: `active?` (default `true`) | `ContactCategory[]` | DIRECTOR, SUPERVISOR (any role that can reach a consuming form) | |
| `POST` | `/contacts/categories` | `{ key, label, color?, sortOrder? }` | `ContactCategory` | **DIRECTOR only** | |
| `PATCH` | `/contacts/categories/:id` | partial | `ContactCategory` | **DIRECTOR only** | |
| `PATCH` | `/contacts/categories/:id/deactivate` | — | `ContactCategory` | **DIRECTOR only** | blocked with a clear error if any active contact still references it (soft guard on top of the DB's `onDelete: Restrict`, which only prevents hard deletion — deactivation needs its own explicit check since Restrict doesn't stop a status flip) |

**Search behavior.** A single `search` string is matched with a case-insensitive `contains` across `fullName`, `organization`, `functionTitle`, `phone`, and `notes` (all five fields the brief lists except "category," which is deliberately a separate structured filter — free-text search against a category *label* would be redundant and less precise than just selecting the category directly in the UI, and mixing structured/unstructured matching in one field tends to produce confusing partial matches). This mirrors the single-`search`-param convention already used by every other module's list endpoint in this codebase (`supplierName`/`authority` filters in the other controllers are the exception, not the rule, and those are being replaced by this very feature).

**Pagination.** Page/pageSize, default `pageSize` 20 for the directory page's paginated view; the `compact` (autocomplete) mode ignores pagination and simply caps results at a fixed limit (e.g. 15) with no page controls — a combobox with more than ~15 suggestions needs a narrower search, not a "next page" affordance.

**Duplicate-warning behavior.** On `POST /contacts` (without `force=true`), the service checks active contacts for: same `phone` (normalized, digits-only comparison) OR same `email` (case-insensitive) OR same `fullName` + `organization` pair (case/accent-insensitive). A match returns `409` with the candidate match's compact shape, letting the frontend show *"Un contact similaire existe déjà — l'utiliser ?"* with two actions: use the existing one (frontend then just selects that `id` instead of creating), or resubmit the same `POST` with `?force=true` to create anyway.

**Deactivate/reactivate behavior.** Both are separate `PATCH` actions (not a generic `active` field on the main update DTO) specifically so they can carry a stricter, different role requirement (`DIRECTOR` only) than the general edit endpoint (`DIRECTOR`+`SUPERVISOR`) without needing per-field permission logic inside one shared handler — this matches the existing codebase's own pattern of separate `.../approve`, `.../reject`, `.../archive` endpoints (each independently role-gated) rather than one omnibus `PATCH` with a status enum body.

**Photo upload behavior.** Standard multipart upload through the existing shared `UploadService`, `folder: 'contacts'`, no size/type restriction beyond what Multer's global config already enforces elsewhere in the app (reuse whatever limit `FileInterceptor` is already configured with in a comparable module, e.g. the 10MB limit seen on ticket/procedure/contract document uploads) — do not invent a new, different limit just for this module.

## 5. Permissions

Verified directly against `hadoum_api/src/auth/guards/roles.guard.ts` / `roles.decorator.ts`: `RolesGuard` reads `@Roles(...)` metadata per-handler (via `Reflector.getAllAndOverride`, checking method-level metadata first, falling back to class-level) and simply checks `roles.includes(request.user.role)`, throwing `ForbiddenException` (403) otherwise. **The brief's requested permission model requires per-endpoint decorators, not one class-level `@Roles(...)` for the whole controller** — confirmed by inspection that `supplier-contracts.controller.ts`, `administrative-procedures.controller.ts`, and `maintenance-tickets.controller.ts` *already* use exactly this fine-grained, per-endpoint style (e.g. create is `@Roles('DIRECTOR')` while approve is `@Roles('SUPERVISOR')` — a real separation-of-duties pattern already established in this codebase), whereas `finances.controller.ts` is the one outlier using a single class-level decorator for everything. **`ContactsController` should follow the supplier-contracts/administrative-procedures/maintenance-tickets style** (per-endpoint), not the finances style, since the brief's requirement (DIRECTOR-only deactivate/reactivate/categories, shared create/edit) cannot be expressed with one class-level decorator at all — this isn't a style preference, it's a hard requirement of the permission model asked for.

| Endpoint | DIRECTOR | SUPERVISOR | EDUCATOR | BOARD |
|---|---|---|---|---|
| `GET /contacts`, `/contacts/:id`, `/contacts/search` (via `compact`), `/contacts/categories` | ✅ | ✅ | ❌ | ❌ |
| `POST /contacts` | ✅ | ✅ | ❌ | ❌ |
| `PATCH /contacts/:id` | ✅ | ✅ | ❌ | ❌ |
| `PATCH /contacts/:id/deactivate`, `/reactivate` | ✅ | ❌ | ❌ | ❌ |
| `POST/PATCH/DELETE /contacts/categories...` | ✅ | ❌ | ❌ | ❌ |
| `POST/GET/DELETE /contacts/:id/photo...` | ✅ | ✅ | ❌ | ❌ |

**Where backend enforcement and frontend hiding are both required — every row above.** Backend `@Roles(...)` is the actual security boundary (a SUPERVISOR calling `PATCH /contacts/:id/deactivate` directly must get a real 403, not just a hidden button); frontend hiding of the "Désactiver"/"Réactiver"/category-management controls for non-DIRECTOR users is a UX layer on top, not a substitute — this matches the pattern already confirmed working in the Module 4 QA campaign, where SUPERVISOR correctly never even sees create buttons on Tickets/Contracts/Procedures/Register (buttons conditionally rendered based on `user.role`, **in addition to** the backend guard, never instead of it). Frontend role checks read `useAuth()`'s `user.role`, matching the existing convention seen in `RegistreEntreesSortiesPage.tsx`'s `isDirector`/`isSupervisor` booleans.

`EDUCATOR` and `BOARD` get no access at all, matching the brief exactly — simply omitted from every `@Roles(...)` array, and the "Répertoire des contacts" sidebar entry (PR 7) is conditionally rendered only for DIRECTOR/SUPERVISOR, following the existing `Sidebar.tsx` pattern of distinct nav arrays per role (already confirmed to exist for DIRECTOR vs SUPERVISOR vs EDUCATOR vs BOARD sections in that file).

## 6. Reusable frontend architecture

**One shared implementation.** All four (eventually five+) consuming forms embed the *same* `ContactAutocomplete` instance type — no per-page reimplementation. This is a direct, deliberate correction of the pattern the earlier audit found broken elsewhere in this codebase (five pages each independently reimplementing their own approve/reject modal) — this feature must not repeat that mistake with contact-picking.

### `useContactSearch` (shared hook, not a component)

- **Responsibility:** owns the debounced search-term state, the `GET /contacts?compact=true&search=...&categoryId=...` fetch, loading/error state, and result caching for the current session (a simple in-memory cache keyed by query string is enough — no need for a heavier data-fetching library given this app currently has none).
- **Returns:** `{ results, loading, error, search, setSearch, categoryFilter, setCategoryFilter }`.
- **Used by:** both `ContactAutocomplete` and (if built) `ContactPickerDialog` — this is *why* a picker dialog doesn't need its own separate data logic if it's ever added: it would just render the same hook's results differently (full modal list vs. inline dropdown), not fetch differently.

### `ContactAutocomplete`

- **Props:** `value: string | null` (selected `contactId`), `onChange: (contactId: string | null, contact?: Contact) => void`, `categoryFilter?: string[]` (restricts/pre-filters by one or more `ContactCategory.key`, e.g. `['FOURNISSEUR']` for Supplier Contracts, `['PRESTATAIRE', 'MAINTENANCE']` for Maintenance Tickets), `placeholder?: string`, `disabled?: boolean`.
- **State responsibilities:** the open/closed dropdown state, the currently-highlighted result index (for keyboard nav), and whether the inline-create modal is open — all local to the component; search state itself is delegated to `useContactSearch`.
- **API calls:** exclusively through `useContactSearch` (list/search) and, when inline-creating, `contacts.api.ts`'s `create` (with duplicate-warning handling — see below).
- **Loading behavior:** a small inline spinner inside the dropdown panel while a search is in flight; the input itself remains editable during loading (never blocks typing).
- **Error behavior:** a inline error row in the dropdown panel ("Erreur de recherche — réessayer") on fetch failure, with results simply empty rather than the whole component crashing; matches the existing app-wide convention of `toast.error(...)` + graceful empty state seen in every other list page's `.catch(() => {})` pattern.
- **Keyboard behavior:** `ArrowDown`/`ArrowUp` move `aria-activedescendant` through the visible result list (wrapping at both ends); `Enter` selects the highlighted result (or, if the "+ Créer un nouveau contact" affordance is highlighted, opens the create modal); `Escape` closes the dropdown without changing `value`; `Tab` closes the dropdown and lets focus move naturally. Implements `role="combobox"` on the input and `role="listbox"`/`role="option"` on the panel/results, per the WAI-ARIA combobox pattern — the first component in this codebase to do so explicitly (existing custom dropdowns like `PosteSelect` in `TeamPage.tsx` do not).
- **Duplicate-warning behavior:** if the inline-create submission returns the `409` duplicate shape from §4, the modal shows the candidate match inline with "Utiliser ce contact" (selects the existing one and closes) and "Créer quand même" (resubmits with `force=true`) — never silently picks one or the other.
- **Create-inline flow:** selecting "+ Créer un nouveau contact" (shown when the current search has no good match, always available as the last row) opens `ContactFormModal` **as an overlay on top of the still-open parent form** (not a navigation away from it), pre-filling `fullName` from whatever text the user had already typed into the autocomplete's search box.
- **Inactive-contact display:** if `value` refers to a contact whose `active` is `false` (fetched via `GET /contacts/:id`, which — per §4 — does not filter out inactive contacts), the component renders it read-only-styled (e.g. greyed text, an "(inactif)" suffix badge) and **does not include it in new search results** for that field going forward — satisfying the brief's "display without allowing selection for new records" requirement precisely: existing selection stays visible, but `useContactSearch`'s query always applies `active=true` server-side by default, so an inactive contact can never be *newly* chosen, only continue being *shown* if it was already the bound value.
- **How the selected contact is returned to the parent form:** `onChange(contactId, contact)` — the parent form stores `contactId` as the field to submit, and optionally uses the full `contact` object immediately for display (e.g. showing organization/phone inline) without needing a second fetch.

### `ContactFormModal`

- **Props:** `initial?: Contact` (edit mode) or none (create mode), `onSaved: (contact: Contact) => void`, `onClose: () => void`, `initialFullName?: string` (for the inline-create-from-autocomplete pre-fill case).
- **State responsibilities:** the form fields themselves, the duplicate-warning inline state, photo-upload progress.
- **API calls:** `contacts.api.ts`'s `create`/`update`, plus `uploadPhoto`/`deletePhoto` if a photo is attached.
- **Everything else** (loading/error/duplicate-warning behavior) matches the pattern already described under `ContactAutocomplete`'s inline-create flow, since that flow *is* this modal — there is exactly one create/edit form implementation, used both from the standalone directory page (PR 7) and from every autocomplete's inline-create affordance (PR 2 onward). This is the second half of "one shared implementation": not just one picker, but one create/edit form too.

### `ContactPickerDialog` — likely not needed

Per §3's PR 7 note: none of the four required integrations (Maintenance Tickets, Expenses, Supplier Contracts, Administrative Procedures) need a full-screen/modal search experience — each embeds `ContactAutocomplete` directly inline in its existing create/edit form, exactly like every other field in those forms already works. A separate picker dialog would only be justified if some future consumer needs to pick a contact from a context where an inline dropdown doesn't fit (e.g., a dense table row with no room for a combobox) — no such case exists in this plan's scope. **Recommendation: do not build `ContactPickerDialog` in PR 1-7; revisit only if a concrete need appears.** This directly answers the brief's "only if justified" instruction — it isn't, yet.

### Existing patterns reused

- List-page shape (search box, filter chips, list, "Nouveau X" button, modal CRUD) — reused from `LocauxPage.tsx`/`SupplierContractsPage.tsx`/etc. for PR 7's `ContactsPage.tsx`.
- Phone auto-formatting (`+221 XX XXX XX XX`) — currently duplicated independently in `TeamPage.tsx` and `ChildrenPage.tsx`; **this plan extracts it into one shared formatter used by `ContactFormModal`**, which both fixes a pre-existing duplication and avoids adding a third copy.
- Toast-based success/error feedback (`sonner`, already used everywhere) — reused as-is.
- Native `window.confirm()` for the deactivate action (matching Spaces'/Procedures' archive-confirmation pattern, confirmed working in the earlier QA campaign) rather than a custom modal — consistent with the *majority* of destructive-ish confirmations already in this codebase, even though administrative-procedures' own "submit" step is the one inconsistent exception noted in the earlier audit (using a custom modal instead). Deactivation here follows the more common native-`confirm()` majority pattern.

## 8. Backfill plan

- **Location:** `hadoum_api/scripts/backfill-contacts.ts`, run via `ts-node` (or the project's existing script-running convention — check for a `hadoum_api/scripts/` precedent at implementation time; if none exists yet, this establishes it) — **not** a NestJS CLI command or an HTTP endpoint, since this is a one-off operational tool that shouldn't be reachable over the network or wired into the running API process.
- **Execution:** `npm run backfill:contacts -- --dry-run` (default) and `npm run backfill:contacts -- --write --mapping=reviewed-mapping.json` (only after human review — see below), added as an `hadoum_api/package.json` script entry.
- **Dry-run mode (default, no flag needed to get it — write mode requires an explicit `--write`):**
  1. For each of the three source fields (`SupplierContract.supplierName`+associated contact fields, `MaintenanceTicket.assignedTo`, `AdministrativeProcedure.assignedTo` — **not** `authority`, per §7's decision not to migrate it) with a non-null, non-empty value: collect distinct values, normalized only by trimming and collapsing internal whitespace and case-folding *for comparison purposes* (the original text is never altered) — **no fuzzy/phonetic matching, no Levenshtein distance, no automatic merging of differently-spelled values.** This is a hard requirement from the brief and this plan does not soften it: "Sénégal Gaz" and "Senegal Gaz SARL" are treated as **two different candidate values** unless a human maps them together via the reviewed-mapping file.
  2. For each distinct normalized value, check for an **exact** match (post-normalization) against an existing active `Contact.fullName`; separately, check for an exact match on `phone`/`email` where the source row has those (only `SupplierContract` currently has parallel `phone`/`email` fields to use this way). Exact matches are proposed as "reuse existing contact #id"; everything else is proposed as "create new contact."
  3. Output: `hadoum_api/scripts/backfill-contacts.report.md` (gitignored, not committed) — a human-readable table: source table, source field, distinct value, proposed action (reuse existing / create new), proposed category, and a count of how many rows would be affected by each. Ambiguous cases — e.g. a normalized value that closely resembles (but doesn't exactly match) an existing contact's name — are listed in a separate "⚠ needs review" section rather than silently defaulting to either merge or create; the script never guesses on the team's behalf.
  4. Alongside the `.md` report, emit `hadoum_api/scripts/backfill-contacts.mapping.json` — a machine-readable draft mapping (`{ sourceValue: { action: "reuse" | "create", contactId?: string, category?: string } }`) that a human edits directly to resolve every "⚠ needs review" entry before write mode will accept it.
- **Write mode (`--write --mapping=<reviewed-file>`):** requires the `--mapping` file to have zero remaining "needs review" entries (the script refuses to run otherwise, with a clear error naming which entries are still unresolved) — this is what makes "no automatic merge without human review" an enforced constraint, not just a documented intention. For each mapping entry: create the `Contact` if the action is "create" (tagged internally, e.g. a `notes` field addendum or a dedicated nullable `backfillBatchId` — **decide at implementation time whether a lightweight batch marker column is worth adding**; if not, the report itself, timestamped, is the audit trail), or reuse the given `contactId`; then update every source row whose normalized value matches to point its new FK column at the resulting contact. **Legacy free-text columns are never modified or cleared by this script, in either mode** — confirmed as a hard requirement, and trivially true here since the script only ever writes to the new FK columns.
- **Dev vs. production behavior:** identical script, identical dry-run-first requirement — no environment-specific branching in the script itself. The difference is procedural: dev can reasonably go dry-run → quick review → write in one sitting; production requires the dry-run report and reviewed mapping to be produced from a **production data snapshot** (or run read-only dry-run directly against production, since dry-run never writes) and reviewed by a human before write mode ever runs against the real production database — and per this project's own established safety rules (confirmed earlier in this engagement), a production run of anything like this happens only with explicit, separate authorization at that time, not as an assumed part of shipping this feature.
- **Rollback:** since nothing is deleted and legacy fields are untouched, rollback means either (a) doing nothing further — the new `Contact` rows and FK links are harmless even if unwanted, since nothing yet depends on them being present (the four integration PRs' UI reads them but degrades gracefully to the legacy field when null, per §7) or (b) a small cleanup query, run manually and deliberately (not as part of the script itself), deleting the specific `Contact` rows created by a given run (identifiable via the timestamped report / batch marker) and nulling the FK columns the run set — never touching legacy free-text data either way.
- **Reconciliation totals after execution:** the script's final output (both dry-run and write mode) includes, per source table: total rows with a non-null source field, rows now linked to a contact, rows still unlinked (and why — e.g. the value was empty to begin with), and total distinct contacts created vs. reused — printed to stdout and appended to the `.md` report, so "did this actually work" is answerable from the run's own output without a separate manual query.

## 10. Risk register

| Risk | Mitigation |
|---|---|
| **Legacy field compatibility** — a page or script still reads `supplierName`/`authority`/`assignedTo` as the sole source of truth after a contact is linked | Dual-write from the frontend the moment a contact is selected (§7); legacy fields are never dropped in this plan's scope; every read site identified by grep in §7 is explicitly listed, not left to be "discovered" later |
| **Notifications using old string fields** — 7 sites in `supplier-contracts.service.ts`, 8 in `administrative-procedures.service.ts` (confirmed by inspection, exact line-bearing greps performed, not estimated) | Each becomes a dual-read (`contact?.fullName ?? legacyField`) in PR 5/PR 6 specifically, not deferred; Maintenance Tickets has **zero** such sites (confirmed), so PR 3 carries none of this risk |
| **Existing exports** | Investigated directly: `hadoum_api/src/reports/` is a generic document-upload/library module (`POST /reports/upload`, `GET /reports`, `GET /reports/:id/url`) — it does **not** read or generate any output from `supplierName`/`authority`/`assignedTo`. No backend "export as CSV/Excel" feature reading these fields exists anywhere in the API. This is a non-risk, confirmed rather than assumed — the "Exporter" buttons seen on `FinancesPage.tsx`/`DirectorDashboard.tsx` during the earlier QA campaign have no backend behind them at all yet. |
| **Inactive contacts still referenced** | `GET /contacts/:id` never filters by `active` (§4); `ContactAutocomplete` renders a bound-but-inactive contact read-only-styled without re-offering it in new search results (§6) |
| **Duplicate contacts** | Service-layer soft duplicate check on create (§4), surfaced as an actionable warning in `ContactFormModal`, not a hard block — reduces but does not claim to eliminate duplicates; the backfill's human-reviewed mapping (§8) is the second, independent line of defense against the same problem at migration time specifically |
| **Two users creating the same contact at the same time (race condition)** | The duplicate check is a read-then-write check with an inherent TOCTOU race under true concurrency; mitigated at the DB level by **not** relying on the duplicate check alone — add a partial unique index consideration is deliberately **not** proposed here (§1 of the earlier architecture doc already reasoned against a hard unique constraint on phone/email, and that reasoning still holds: real contact data is too messy for a hard constraint). Accepted residual risk: a rare simultaneous double-create could produce two near-identical rows; this is caught later by the same reconciliation process the backfill uses (§8), not prevented outright. Called out explicitly rather than glossed over, since the brief specifically asks about it. |
| **S3 photo failures** | Reuses `UploadService`'s existing error handling (`InternalServerErrorException` with the underlying S3 error message, already the established pattern for every other upload in the app) — a failed photo upload does not fail the surrounding contact create/update, since photo upload is a separate endpoint (`POST /contacts/:id/photo`) called only after the contact itself already exists |
| **Frontend duplication** | The entire point of §6 — one `ContactAutocomplete`, one `ContactFormModal`, shared across every consumer; explicitly named as a process/discipline risk in the earlier architecture doc (the five-duplicated-validation-modals precedent) and directly designed against here |
| **Migrations on existing production data** | PR 1's migration is additive-only (§2) — no risk to existing data by construction, since nothing existing is altered, only new tables/nullable columns added. The only step in this whole plan that writes derived data from existing production rows is the backfill (PR 8), which is dry-run-gated and requires human-reviewed mapping before any write mode run, and production execution requires separate explicit authorization per this engagement's established safety rules |
| **Rollback after a partial deployment** (e.g., PR 5 shipped, PR 6 didn't yet) | Every PR in §3 is independently revertible without affecting the others, *because* every relation is nullable and every legacy field stays intact throughout — there is no PR in this plan that requires a later PR to already be deployed for the earlier one to keep working correctly on its own |
| **`SupplierContract` tests depending on `supplierName`** | Confirmed the exact file: `hadoum_api/src/supplier-contracts/supplier-contracts.service.spec.ts` (plus `test/lifecycle-scenarios.e2e-spec.ts`) construct/assert contracts via the raw `supplierName` field today. Since `supplierName` is **not removed** by this plan, these tests continue to pass unmodified through PR 5 — the required test changes are additive (new tests for the `supplierContactId` path), not corrective. This should be verified precisely (read the actual assertions) at PR 5's implementation time rather than assumed identical to what's described here, since test files are exactly the kind of thing that can drift between planning and implementation. |
